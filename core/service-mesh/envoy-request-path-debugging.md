# Envoy Request-Path, Timeout, Reset, and 504 Debugging

This chapter is the canonical foundation for diagnosing service-mesh and proxy request failures across Envoy, Istio, gateways, sidecars, ambient dataplanes, and upstream services.

## Interview answer in 90 seconds

> I debug an Envoy 504 or reset by identifying the proxy that generated the response and reconstructing the exact request path. I separate downstream time, proxy queueing and connection establishment, upstream service time, retries, and response transfer. Then I compare affected and healthy cohorts by route, cluster, endpoint, zone, version, protocol, and proxy configuration. Envoy response flags, access logs, config dumps, stats, traces, and packet evidence tell me whether the failure is no healthy upstream, connect timeout, upstream response timeout, reset, TLS failure, circuit breaking, outlier ejection, or a downstream cancellation. I verify the effective route and cluster configuration rather than assuming the control plane delivered what was intended. Mitigation is narrow: stop a bad rollout, restore endpoints, remove a harmful retry, extend a timeout only when the latency budget supports it, or route around a failed cohort. Recovery is proven from the client journey and by normal upstream success, latency, connection, retry, and ejection signals.

## Request path

```text
client
  |
  v
ingress / edge gateway
  |
  v
downstream Envoy listener
  |
  v
filter chain -> route -> cluster
  |
  v
load balancing -> upstream connection pool
  |
  v
upstream Envoy or application
  |
  v
dependency chain
```

A single user request may cross several proxies. Always determine which hop produced the status or reset.

## Start with ownership of the error

A 504 can be generated by:

- external CDN or load balancer;
- ingress gateway;
- sidecar or waypoint proxy;
- application gateway;
- application code;
- client library translating a timeout.

Evidence:

- response headers;
- proxy access logs;
- trace span status;
- request ID and timing;
- source and destination addresses;
- Envoy response flags;
- status details.

Do not assume every 504 means the upstream application timed out.

## Latency decomposition

```text
client_observed_latency =
    network_to_proxy
  + proxy_queue_or_filter_time
  + upstream_connect_time
  + upstream_request_time
  + retry_or_hedge_time
  + response_transfer
```

Track:

- downstream request duration;
- upstream service time;
- connection establishment;
- DNS or discovery delay;
- pending requests in connection pools;
- retry attempts;
- stream resets;
- response bytes and transfer time;
- caller deadline and cancellation.

## Common Envoy failure categories

### No healthy upstream

Likely causes:

- empty EDS or EndpointSlice set;
- readiness removed all endpoints;
- locality or subset routing selects no endpoints;
- all endpoints ejected;
- service export/import or discovery scope error;
- cluster not warmed or configuration rejected;
- endpoint health is stale.

### Connect timeout

Likely causes:

- network path or security policy;
- wrong port or protocol;
- upstream not listening;
- SYN loss or routing failure;
- connection backlog saturation;
- TLS handshake delay;
- stale endpoint address;
- cross-zone or gateway path failure.

### Upstream response timeout

Likely causes:

- application or dependency latency;
- queueing and saturation;
- route timeout shorter than expected service time;
- retry consumed the deadline;
- streaming request incorrectly given a short timeout;
- response transfer stalled;
- head-of-line blocking.

### Reset before response

Likely causes:

- upstream process restart;
- connection pool reset;
- protocol mismatch;
- HTTP/2 stream or connection limits;
- downstream cancellation;
- proxy drain during rollout;
- TLS or connection termination;
- local overload protection.

### Circuit breaking

Envoy can reject work when connection, pending-request, request, retry, or connection-pool limits are reached.

A circuit-breaker rejection is often the protective symptom, not the root cause. Identify why concurrency or pending work rose.

### Outlier ejection

Outlier detection can protect traffic from failing endpoints, but aggressive settings can eject too many endpoints and collapse capacity.

Check:

- ejection reason;
- maximum ejection percentage;
- base ejection time;
- consecutive error thresholds;
- panic threshold and load-balancing behavior;
- whether failures are endpoint-local or dependency-wide.

### Retry amplification

Retries can produce:

- higher upstream concurrency;
- repeated work after caller deadline;
- synchronized waves;
- cross-zone traffic;
- duplicate side effects;
- hidden first-attempt failures.

Use one retry owner, budgets, idempotency, backoff, and remaining-deadline checks.

## Envoy response flags

Exact flags vary by version, but common categories include:

- upstream connection failure;
- upstream reset;
- upstream request timeout;
- no healthy upstream;
- rate limiting or overload;
- local reset;
- downstream termination;
- response from cache or local reply.

Treat the flag as a starting classification. Correlate it with cluster, endpoint, timing, and upstream evidence.

## Configuration truth

The desired Istio or control-plane object is not the same as the effective proxy configuration.

Verify:

- listener and filter chain;
- virtual host and route match;
- route timeout and retry policy;
- destination cluster;
- subset and locality rules;
- endpoint membership;
- TLS transport socket;
- circuit-breaker and outlier settings;
- config version and last update;
- ACK/NACK status;
- warming or rejected resources.

Useful commands in Istio environments:

```bash
istioctl proxy-status
istioctl proxy-config listeners <pod> -n <namespace>
istioctl proxy-config routes <pod> -n <namespace>
istioctl proxy-config clusters <pod> -n <namespace>
istioctl proxy-config endpoints <pod> -n <namespace>
istioctl proxy-config log <pod> -n <namespace>
```

Direct Envoy admin endpoints may provide:

```text
/config_dump
/stats
/clusters
/listeners
/server_info
```

Protect admin endpoints; do not expose them broadly.

## Cohort analysis

Compare failures by:

- source workload and proxy version;
- destination service and endpoint version;
- route, host, method, and protocol;
- zone, region, cluster, and network;
- mesh revision;
- mTLS mode and identity;
- connection-pool state;
- release and configuration hash;
- retry attempt;
- long-lived versus new connections.

A partial outage after deployment often maps to one proxy revision, subset, endpoint pool, locality, or connection cohort.

## Evidence hierarchy

1. client-observed status and latency;
2. gateway and sidecar access logs;
3. traces showing hop and retry timing;
4. Envoy cluster, connection, pending, retry, and reset stats;
5. effective config dump;
6. endpoint and discovery state;
7. application logs and profiles;
8. packet capture when protocol or network evidence remains ambiguous;
9. recent release and configuration changes.

## Investigation flow

### 1. Reproduce safely

Use a known request with:

- trace/request ID;
- source location;
- exact host and route;
- deadline;
- expected response;
- repeated samples from healthy and affected cohorts.

### 2. Identify the failing hop

At each proxy ask:

- did it receive the request?
- which route and cluster matched?
- was an upstream selected?
- was a connection established?
- did the upstream respond?
- was there a retry?
- who reset or timed out?

### 3. Validate endpoint and connection state

Check:

- endpoint count and locality;
- health and ejection;
- active and pending connections;
- upstream request concurrency;
- connection reuse;
- protocol negotiation;
- DNS/discovery freshness;
- network policy and security groups where relevant.

### 4. Compare effective configuration

Diff a healthy and affected proxy by configuration version and relevant listener/route/cluster/endpoint sections.

### 5. Check application and dependency saturation

Proxy symptoms can be caused by:

- slow application threads;
- connection pool exhaustion;
- database or cache latency;
- CPU throttling;
- GC pauses;
- lock contention;
- downstream retries;
- queue backlog.

## Safe mitigations

Preferred order:

1. stop a bad application, proxy, or configuration rollout;
2. remove or isolate a failing endpoint cohort;
3. restore discovery or endpoint health;
4. disable a harmful retry or hedge policy;
5. reduce concurrency or shed optional traffic;
6. restore known-good route, cluster, or TLS configuration;
7. extend a timeout only after verifying the end-to-end deadline and resource impact;
8. add capacity only at the proven bottleneck;
9. drain or restart proxies selectively when configuration or connection state is confirmed bad.

A mass proxy restart can cause connection, TLS, DNS, and discovery storms.

## Timeout design

Timeouts should be hierarchical:

```text
client deadline
  > gateway route budget
  > service budget
  > downstream call budgets
```

Include queueing, retries, and response margin. Streaming and long-poll operations require explicit semantics rather than the default request timeout.

Increasing a timeout can worsen saturation by retaining work and connections longer.

## Connection pools

Monitor:

- active and pending connections;
- requests per connection;
- max connections and pending requests;
- HTTP/2 stream limits;
- connection establishment failures;
- connection lifetime and draining;
- upstream keepalive;
- DNS refresh or endpoint churn;
- source-port and NAT constraints outside the proxy.

A low connection limit can queue healthy work; an unlimited pool can overload the upstream.

## Protocol pitfalls

- HTTP/1.1 versus HTTP/2 mismatch;
- cleartext versus TLS mismatch;
- gRPC timeout and status translation;
- WebSocket upgrade handling;
- streaming idle timeout;
- server-first protocols;
- ALPN negotiation;
- connection coalescing assumptions;
- request body buffering and size limits.

## SLOs and signals

Track by route and cluster:

- downstream success and latency;
- upstream success and service time;
- local replies;
- no-healthy-upstream count;
- connection failures;
- pending request saturation;
- resets by source;
- timeout count;
- retry attempts and success;
- circuit-breaker rejection;
- outlier ejection;
- config convergence and NACKs;
- endpoint freshness.

## Weak answers to avoid

- “Increase the 504 timeout.”
- “Restart Envoy.”
- “The app is slow.”
- “Istio is broken.”
- “All pods are Ready, so endpoints are healthy.”
- “Enable three retries.”
- “Disable circuit breakers.”

## Adversarial follow-ups

### Why can only some users fail?

They may route through one gateway, zone, proxy revision, route subset, endpoint cohort, long-lived connection, DNS answer, or data shard.

### When would you restart a proxy?

When evidence shows bad local state, stuck connection pools, or failed configuration convergence that cannot be repaired more narrowly. Restart a bounded cohort and watch connection and discovery load.

### Why can timeout increases make the incident worse?

They retain concurrency and queue entries longer, allowing more callers to accumulate while the real bottleneck remains saturated.

### How do you prove the control plane is not the issue?

Show the affected proxy has the intended, accepted effective configuration and fresh endpoints, then isolate the failure to connection, upstream, or dependency behavior. A healthy control-plane dashboard alone is insufficient.

### What proves recovery?

Client SLIs recover, proxy local-reply and reset rates normalize, upstream latency and success recover, retries and pending requests return to baseline, and the previously affected cohort succeeds without relying on hidden fallback.

## Principal-level review checklist

- error ownership is identified at the exact hop;
- route, cluster, endpoint, and transport configuration are verified from the proxy;
- deadlines and retries are budgeted end to end;
- connection and pending-request limits protect the upstream;
- outlier ejection cannot remove unsafe amounts of capacity;
- cohorts include proxy revision and locality;
- admin and debug interfaces are protected;
- mitigation avoids fleet-wide restart storms;
- mesh SLIs include convergence, local replies, resets, and endpoint freshness;
- game days cover timeout, discovery, TLS, gateway, and control-plane failure.
