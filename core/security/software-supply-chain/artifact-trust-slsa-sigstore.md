# Artifact Trust, SLSA Provenance, SBOMs, Sigstore, and Deployment Verification

## Why this exists

A secure runtime cannot compensate for an untrusted build pipeline. If an attacker can alter source, dependencies, build instructions, build workers, registry content, deployment manifests, or verification policy, the platform may reliably deploy malicious software.

Software supply-chain security creates verifiable links between:

- the source revision that was intended;
- the build platform that produced the artifact;
- the dependencies and parameters used;
- the immutable artifact digest;
- the identity that signed or attested to the result;
- the policy that allowed deployment;
- the runtime instances currently executing it.

## What the interviewer is testing

A Staff or Principal candidate should be able to:

- threat-model source, build, dependency, registry, and deployment paths;
- distinguish signatures, provenance, attestations, and SBOMs;
- explain digest pinning and why tags are insufficient;
- use SLSA as a maturity framework without treating it as a product;
- describe Sigstore and Cosign keyless or key-based trust models;
- design deployment verification that survives outages and emergency rollback;
- define builder isolation, identity, evidence retention, and incident response;
- avoid collecting attestations that no consumer verifies.

## Threat model

Consider attacks against:

### Source

- compromised maintainer account;
- bypassed branch protection;
- malicious pull request or dependency update;
- altered release tag;
- source archive that does not match the reviewed revision.

### Build

- untrusted build worker;
- cross-build contamination;
- mutable runner image;
- leaked signing credential;
- build script or environment modified outside review;
- provenance generated by the project rather than the trusted builder;
- artifact substitution after tests complete.

### Dependencies

- dependency confusion;
- typosquatting;
- compromised package release;
- mutable base-image tag;
- unreviewed transitive dependency;
- unavailable or poisoned package mirror.

### Distribution

- registry credential theft;
- tag replacement;
- artifact deletion or rollback substitution;
- replication inconsistency;
- signature or attestation removal;
- unauthorized registry promotion.

### Deployment

- manifest references a tag instead of a digest;
- admission verification is disabled or fails open unexpectedly;
- policy trusts an overly broad identity;
- emergency process bypasses evidence without audit;
- a valid signature is accepted from an unauthorized signer;
- provenance is present but not checked against expected source or builder.

## Core evidence types

### Digest

A content digest identifies exact bytes. Container images should be promoted and deployed by digest.

```text
registry.example.com/payments/api@sha256:...
```

A tag such as `v1.4.2` is a mutable name unless the registry enforces immutability. A signature over a digest protects artifact identity; a signature over a mutable tag does not make the tag immutable.

### Signature

A signature proves that a key or identity approved a specific payload. Verification must answer:

- Which identity is trusted?
- For which repository, workflow, environment, and time?
- Which issuer or certificate authority is trusted?
- Was the signature bound to the artifact digest?
- Was revocation, expiry, or transparency evidence evaluated?

Cryptographic validity alone is not authorization.

### Provenance

Provenance describes how an artifact was produced. Useful fields include:

- artifact subject and digest;
- source repository and revision;
- build definition or workflow;
- builder identity;
- build parameters;
- dependencies or materials;
- invocation and timing metadata;
- completeness and reproducibility information.

Provenance is valuable only when generated and signed by a builder whose identity and isolation properties the verifier trusts.

### Attestation

An attestation is a signed statement about an artifact. Examples:

- build provenance;
- vulnerability scan result;
- test result;
- policy approval;
- SBOM location or digest;
- release authorization;
- deployment evidence.

The verifier must validate both the signature and the semantic predicate.

### SBOM

A Software Bill of Materials inventories components and dependencies. It supports vulnerability response, license analysis, and impact scoping.

An SBOM does not prove:

- the listed components were actually used;
- the build was not tampered with;
- the artifact is safe;
- the dependencies were reviewed;
- the artifact came from an approved source.

Bind the SBOM or its digest to the artifact and retain generation metadata.

## SLSA model

SLSA defines requirements and levels for software supply-chain integrity. The Build track focuses on increasing trust in provenance and build-platform behavior.

Use SLSA to answer:

- Is provenance available?
- Is it generated by the build platform rather than the project?
- Is the provenance authenticated?
- Is the builder isolated against tampering and cross-build influence?
- Can consumers verify the artifact against expected source and builder policy?

Do not say "we use SLSA" without naming the track, level, artifact population, builder, and verification process.

## End-to-end trust flow

```text
1. Developer proposes a reviewed source change.
2. Protected source control records the approved revision.
3. A trusted build identity starts an isolated build.
4. Dependencies are resolved through controlled sources.
5. The builder produces an artifact and immutable digest.
6. The builder emits signed provenance for that digest.
7. Additional systems attach SBOM, test, and scan attestations.
8. The registry stores the artifact and associated evidence.
9. Promotion references the digest, not a rebuilt artifact.
10. Deployment policy verifies identity, source, builder, and predicates.
11. Runtime inventory records the deployed digest and evidence decision.
```

Rebuilding separately for each environment breaks artifact identity and complicates incident analysis. Prefer build once, verify, and promote the same digest.

## Builder trust boundary

The build platform is a privileged security product.

Controls include:

- ephemeral and isolated workers;
- clean workspace for every build;
- minimal network access;
- pinned and verified runner images;
- short-lived workload identity;
- no long-lived signing key in project secrets;
- protected build configuration;
- separation between project code and provenance generation;
- restricted access to release and signing workflows;
- immutable build logs and evidence;
- tenant isolation between builds;
- tested worker destruction and credential revocation.

A build that can modify its own provenance or access another project's signing authority does not provide strong evidence.

## Sigstore and Cosign

Sigstore provides an ecosystem for signing and verifying software artifacts. Cosign is commonly used to sign container images and blobs, attach attestations, and verify signatures and predicates.

### Keyless signing

In a keyless flow:

```text
workload or user identity
  -> OpenID Connect token
  -> short-lived signing certificate
  -> artifact signature
  -> transparency evidence
```

The verifier checks the certificate identity and issuer rather than distributing a long-lived public key for every signer.

Policy must narrow identity carefully. Trusting any identity from a broad issuer is unsafe. Bind trust to expected workflow, repository, branch or tag, and environment where the certificate claims support it.

### Key-based signing

Keys may be stored in KMS, HSM, or hardware tokens. This can fit controlled release authorities, offline roots, or environments without an appropriate keyless identity flow.

Requirements:

- rotation and revocation process;
- least-privilege signing access;
- separation between build and administrative identities;
- audit logs;
- backup and recovery for required keys;
- no exportable key in CI secrets when KMS signing is available.

### Verification

A strong verification policy checks:

- artifact digest;
- signature validity;
- trusted certificate issuer or key;
- exact signer identity pattern;
- transparency or bundle evidence as required;
- attestation type;
- expected source repository and revision;
- approved builder identity;
- policy-specific predicates such as tests or scan age.

Example conceptual command:

```bash
cosign verify \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity-regexp '^https://github.com/example/payments/.github/workflows/release.yaml@refs/tags/' \
  registry.example.com/payments/api@sha256:...
```

Exact identity claims and command flags depend on the signing environment and deployed Cosign release.

## Provenance policy

Verification should compare provenance against expected values.

Example policy questions:

```text
subject digest == deployment image digest?
source repository == approved repository?
source revision == reviewed release revision?
builder identity == approved hardened builder?
build workflow == protected release workflow?
build parameters == allowed parameters?
dependencies or materials satisfy policy?
provenance generated after source approval?
```

Presence of provenance is not enough. A malicious project can attach truthful provenance showing that it built from an unauthorized source unless policy rejects it.

## SBOM and vulnerability workflow

Recommended flow:

```text
Build artifact
  -> generate SBOM
  -> bind SBOM digest to artifact
  -> scan artifact and SBOM
  -> sign scan attestation
  -> evaluate admission policy
  -> continuously rescan inventory as vulnerability data changes
```

Admission-time scanning alone becomes stale immediately. Retain runtime inventory by digest and reevaluate when vulnerability intelligence changes.

Avoid blocking every deployment on a live external scanner call. Prefer precomputed signed results with bounded age and clear emergency behavior.

## Registry design

Controls:

- immutable production tags or digest-only promotion;
- separate build, staging, and production repositories where useful;
- explicit promotion authorization;
- retention policies that preserve rollback artifacts and evidence;
- replication consistency monitoring;
- restricted delete permissions;
- malware and vulnerability scanning;
- registry audit logs;
- signature and attestation retention;
- protection against cross-tenant repository access.

Do not garbage-collect the only artifact required for emergency rollback.

## Deployment policy

A deployment policy should answer three layers.

### Identity

Who signed or attested?

### Integrity

Does the evidence apply to the exact artifact digest?

### Authorization and semantics

Was the artifact produced from approved source by an approved builder, and do required predicates pass?

Example environment policy:

```text
Development:
  digest required
  approved registry
  signature warning

Staging:
  digest required
  trusted signature required
  provenance required
  SBOM required

Production:
  all staging controls
  protected source revision
  approved builder identity
  release authorization attestation
  vulnerability policy within bounded age
  no expired exception
```

Use progressive enforcement and measure false positives before production-wide deny.

## Policy engine options

Verification may be implemented through:

- Sigstore policy-controller;
- Kyverno image validation policy;
- Gatekeeper with a trusted external-data provider;
- cloud-provider admission or registry controls;
- CI and GitOps promotion checks;
- custom deployment-controller verification.

Choose one authoritative admission decision where possible. Multiple independent verifiers with different trust roots create inconsistent behavior.

## Offline and outage behavior

Supply-chain controls depend on identity providers, certificate roots, transparency data, registries, policy engines, and attestation storage.

Design for:

- cached or bundled verification material;
- trusted-root rotation;
- registry or transparency-service outage;
- policy-controller outage;
- air-gapped environments;
- disaster recovery in another region;
- rollback when the original builder is unavailable;
- emergency deployment with explicit approval and expiry.

Fail-closed behavior protects integrity but can block incident recovery. Pre-stage trusted rollback artifacts and verification bundles so emergencies do not require disabling policy globally.

## Exceptions and emergency releases

An emergency path should not mean "skip verification."

Prefer:

- a separate highly controlled release identity;
- two-person approval;
- digest-only artifact reference;
- minimal scoped exception;
- immutable audit record;
- short expiry;
- post-event review;
- mandatory replacement by a normal trusted build.

Never create a permanent annotation that lets any namespace bypass signature policy.

## Secrets and identity in CI

- use workload identity federation from CI to cloud and registries;
- avoid static cloud keys and registry passwords;
- scope tokens to repository, workflow, branch, and environment;
- separate pull-request and release permissions;
- deny untrusted forked code access to release credentials;
- protect reusable workflows and action versions;
- pin third-party actions or plugins by immutable revision;
- review OIDC subject and audience claims;
- monitor token exchange and signing events.

The CI identity is often more important than the developer laptop identity because it can create trusted release evidence.

## Dependency controls

- use approved registries and mirrors;
- lock dependency versions and hashes;
- pin base images by digest;
- monitor abandoned and compromised packages;
- restrict installation scripts and build-time network access;
- separate dependency update automation from automatic release authority;
- verify package signatures where ecosystems support it;
- retain dependency resolution evidence;
- test reproducibility where valuable.

A lockfile improves repeatability but does not prove the dependency is trustworthy.

## Runtime inventory and response

Maintain a queryable mapping:

```text
service
  -> environment
  -> cluster or runtime
  -> artifact digest
  -> source revision
  -> builder
  -> provenance
  -> SBOM
  -> vulnerability findings
  -> deployment time
  -> owner
```

This supports rapid response when:

- a signing identity is compromised;
- a builder is found vulnerable;
- a dependency CVE appears;
- a registry repository is altered;
- a source revision is revoked;
- a policy bug admitted untrusted artifacts.

## Incident response

For suspected supply-chain compromise:

1. Establish incident command and stop affected promotions.
2. Preserve source, CI, identity, registry, transparency, and deployment evidence.
3. Identify affected builder identity, source revisions, artifact digests, and environments.
4. Revoke credentials, keys, tokens, or trust policy narrowly.
5. Quarantine or stop affected artifacts based on impact.
6. Rebuild from a trusted builder and source revision.
7. Verify replacement provenance and attestations independently.
8. rotate trust roots or release identities if needed.
9. Search runtime inventory for all related digests and materials.
10. Repair the control and run a game day before resuming normal release.

Deleting the image from one registry tag is not containment if the digest is mirrored or already running.

## Observability and SLOs

Measure:

- percentage of production artifacts deployed by digest;
- signature and provenance coverage;
- percentage verified against approved builder and source policy;
- SBOM coverage and freshness;
- attestation verification latency and failure rate;
- admission-controller availability;
- untrusted artifact rejection count;
- active exception count and age;
- time to identify all deployments affected by a digest, builder, or dependency;
- trusted builder conformance and isolation test success;
- rollback artifact availability;
- time to revoke a compromised signing identity.

A useful platform objective is not "100% signed" but "100% of production deployments are authorized by identity and semantic provenance policy."

## Rollout plan

1. Inventory build systems, registries, and deployment paths.
2. Require digest references and registry allow-lists.
3. Generate SBOM and provenance without enforcement.
4. Sign artifacts through workload identity or protected KMS.
5. Verify signatures in CI and promotion workflows.
6. Compare provenance against source and builder policy.
7. Run admission in audit or warning mode.
8. Fix templates, rollback artifacts, and emergency process.
9. Enforce by environment and workload cohort.
10. Continuously evaluate runtime inventory and trust-root changes.

## 90-second interview answer

> I design software supply-chain security around exact artifact identity and verifiable production history. We build once, promote the same digest, and never rely on mutable tags for production. A trusted isolated builder emits authenticated provenance for the artifact digest; additional systems attach SBOM, test, scan, and release attestations. With Sigstore and Cosign, verification checks not only cryptographic validity but the exact OIDC issuer and signer identity, approved source repository and revision, builder identity, and required predicates. SLSA provides a maturity framework for provenance and builder trust, but I name the track and level rather than claiming generic compliance. Admission policy verifies the digest and evidence before deployment, while runtime inventory maps every deployed digest back to source, builder, SBOM, and owner. I stage enforcement from evidence generation to audit, warning, and canary deny. I pre-stage trusted rollback artifacts and bundles so an external-service outage does not force us to disable verification during an incident.

## Adversarial follow-ups

### "Is a signed image trusted?"

Only if the signer identity is authorized for that artifact and environment, the signature covers the exact digest, and required provenance and predicate policy pass.

### "What does an SBOM protect?"

It improves inventory and response. It does not prove build integrity, artifact safety, or dependency approval.

### "Why use keyless signing?"

It reduces long-lived signing-key distribution and binds signatures to short-lived workload or user identity. It still requires strict issuer and identity policy and trusted-root operation.

### "What happens when the transparency or identity service is down?"

Use trusted verification bundles or cached roots where supported, pre-stage rollback artifacts, and define a narrowly audited emergency path. Do not disable policy globally.

### "Do you rebuild for production?"

No. I promote the tested artifact digest. Rebuilding creates a different artifact and breaks the evidence chain.

## Dangerous answers

- "The image is safe because it is signed."
- "SLSA is a scanner."
- "An SBOM proves the artifact contains no vulnerabilities."
- "We trust every identity from our CI issuer."
- "Tags are immutable because teams agree not to move them."
- "Admission can call the scanner live for every pod."
- "Emergency deploy means bypass all verification."

```text
Protected source

  -> registry
  -> identity + integrity + semantic verification
  -> deployment
  -> runtime inventory
  -> revocation and incident response
```
