# 1. Architecture, Boot, Privilege Boundaries, and Syscalls

## 1.1 Production mental model

Linux is a monolithic kernel with loadable modules. Core subsystems execute in one privileged address space and communicate through direct internal calls.

```text
+----------------------------------------------------------+
| Userspace                                                |
| application | runtime | libc | agents | system services |
+---------------- system-call / exception boundary --------+
| Kernel                                                   |
| scheduler | VM | VFS | block | TCP/IP | LSM | drivers   |
+---------------------- hardware boundary -----------------+
| CPU | RAM | NIC | NVMe | accelerator | firmware         |
+----------------------------------------------------------+
```

“Monolithic” does not mean unstructured. Linux has mature subsystem interfaces, but a serious kernel or driver defect can compromise or crash the entire host. Isolation inside one shared kernel is therefore not equivalent to hypervisor isolation.

A Staff-level diagnosis connects an application symptom to the underlying kernel path. “The node is slow” is not actionable. Determine whether work is waiting for CPU, a lock, memory reclaim, storage, a socket, a device, or a remote dependency.

## 1.2 User mode and kernel mode

Applications normally execute without permission to access arbitrary physical memory, program devices, modify page tables, or execute privileged instructions. The kernel runs with those privileges.

Transitions into the kernel occur through:

- System calls initiated by userspace.
- Exceptions such as page faults and divide-by-zero.
- Hardware interrupts generated by devices.
- Inter-processor interrupts for cross-CPU coordination.

A privilege transition is not automatically a scheduler context switch. A thread can enter the kernel for `read()` and return to itself. A task switch occurs only when the scheduler selects another runnable task.

## 1.3 Boot path

```text
power on
  -> firmware (UEFI/BIOS)
  -> boot manager / bootloader
  -> kernel image + initramfs
  -> early kernel initialization
  -> root filesystem discovery
  -> exec PID 1
  -> dependency-ordered system services
  -> workload startup
```

### Firmware

Firmware initializes enough CPU, memory, and device state to locate a boot target. Common failures include:

- Invalid or missing UEFI boot entry.
- Boot device unavailable.
- Secure Boot rejecting an unsigned component.
- Firmware or hardware initialization hanging.

### Bootloader

The bootloader selects a kernel, initramfs, and command line. Kernel arguments can change root-device selection, console behavior, cgroup mode, IOMMU, crash-dump reservation, security, and performance characteristics.

Useful evidence:

```bash
cat /proc/cmdline
bootctl status 2>/dev/null || true
grub-editenv list 2>/dev/null || true
```

### Kernel initialization

The kernel typically:

1. Decompresses itself.
2. Establishes early page tables.
3. Discovers CPU, memory, and NUMA topology.
4. Initializes interrupts, timers, allocators, and core subsystems.
5. Starts secondary CPUs.
6. Initializes built-in drivers.
7. Mounts initramfs as a temporary root.

### initramfs

The initramfs contains early userspace required before the real root filesystem is accessible. It may load storage, RAID, LVM, encryption, network, and filesystem components.

Classic failure:

> The kernel starts, but the host drops into an initramfs emergency shell because the root logical volume, encrypted device, or storage controller cannot be discovered.

Evidence:

```bash
cat /proc/cmdline
lsmod
lsblk -f
blkid
dmesg -T | tail -200
```

### PID 1

After mounting the real root, the kernel executes the init process, usually `systemd`.

PID 1 is special because it:

- Adopts orphaned children.
- Must reap exited children to prevent zombie accumulation.
- Has special signal semantics.
- Is generally critical to system survival.

A container's first process is also PID 1 inside its PID namespace. An application that does not forward signals or reap children can behave correctly on a normal shell and incorrectly as a container entrypoint.

## 1.4 systemd as dependency graph and supervisor

Treat systemd as a graph scheduler, activation system, and cgroup-aware supervisor.

Important relationships:

- `Requires=` creates a hard requirement.
- `Wants=` creates a weaker requirement.
- `After=` and `Before=` define ordering, not dependency.
- Socket, path, timer, mount, and device units can activate services.
- Service cgroups provide reliable process ownership.

Commands:

```bash
systemd-analyze time
systemd-analyze critical-chain
systemd-analyze blame
systemctl list-dependencies --reverse some.service
systemctl show some.service -p ActiveState,SubState,MainPID,ControlGroup
journalctl -b -u some.service
```

Interview trap:

> `After=network.target` does not prove DNS, routing, credentials, or an external dependency is usable. It provides ordering against a loosely defined target. Applications still need explicit readiness, deadlines, retries, and failure policy.

## 1.5 System-call path

A syscall is a controlled request for kernel work.

```text
application
   -> runtime or libc wrapper
   -> architecture syscall instruction
   -> syscall entry code
   -> kernel subsystem
   -> authorization / LSM hooks
   -> data structure, driver, or device
   -> return to userspace
```

Examples:

- `openat()` enters pathname lookup and VFS authorization.
- `read()` may copy from page cache, block on storage, or consume a pipe/socket.
- `connect()` may trigger routing, neighbor discovery, policy, and TCP handshake state.
- `futex()` allows contended userspace locks to sleep and wake efficiently.
- `epoll_wait()` blocks until registered descriptors become ready.

A syscall's cost may come from cache misses, locks, copying, path traversal, scheduler delay, page faults, device latency, or remote dependencies—not merely the privilege transition.

## 1.6 Blocking, nonblocking, readiness, and completion

These terms are often mixed together:

- **Blocking:** the calling thread sleeps until progress, signal, or timeout.
- **Nonblocking:** the operation returns immediately when it cannot progress, often with `EAGAIN`.
- **Synchronous:** completion is observed in the current control flow.
- **Asynchronous:** submission and completion are decoupled.

Nonblocking sockets plus `epoll` are usually readiness-based: the application is told an operation is likely to progress, then performs it. `io_uring` can provide completion-oriented submission for many operation types.

## 1.7 Copies and so-called zero-copy

A simple path can move data multiple times:

```text
storage -> page cache -> userspace buffer -> socket buffer -> NIC
```

Mechanisms such as `sendfile()`, `splice()`, memory mapping, direct I/O, and device offloads can reduce CPU-mediated copies or per-packet work.

Trade-offs:

- Page cache improves locality but can create reclaim and dirty-page pressure.
- Direct I/O avoids normal page-cache data caching but transfers cache and alignment responsibility to the application.
- Offloads reduce CPU but can make captures differ from wire behavior.
- “Zero-copy” usually means fewer CPU copies, not that bytes never move.

## 1.8 Page faults

A valid virtual access whose mapping is absent triggers a page fault. The kernel may:

- Map an already resident page.
- Allocate a zero-filled anonymous page.
- Read file data from storage.
- Perform copy-on-write.
- Deliver `SIGSEGV` for an invalid access.

Faults are fundamental to demand paging and are not inherently errors. The operational question is whether fault rate and fault latency are compatible with the SLO.

## 1.9 Interrupts and deferred work

Device interrupts must be acknowledged quickly. Linux commonly performs minimal top-half work and defers heavier processing through softirqs, threaded IRQs, workqueues, or related mechanisms.

Network processing can consume substantial softirq CPU. When it falls behind, backlog and drops may increase while application profiles look normal.

```bash
cat /proc/interrupts
cat /proc/softirqs
mpstat -P ALL 1
sar -I SUM 1
```

Questions:

- Is one CPU handling most device interrupts?
- Is `ksoftirqd` active because deferred work exceeded interrupt-context budget?
- Are IRQ affinity and receive-side scaling aligned with NUMA locality?
- Where exactly are packets dropped: NIC, driver, kernel backlog, socket queue, or application?

## 1.10 Modules and drivers

Kernel modules allow dynamic extension, especially for drivers and filesystems.

```bash
lsmod
modinfo <module>
find /sys/module/<module>/parameters -maxdepth 1 -type f -print
```

Operational risks:

- Driver bugs can hang or panic the host.
- Out-of-tree modules complicate upgrades and support.
- Dynamic module loading expands attack surface.
- Module parameters can silently alter behavior.

For immutable fleets, prefer a tested kernel and module set, reproducible node images, and replacement over long-lived in-place mutation.

## 1.11 Kernel logs and crash evidence

```bash
dmesg -T
journalctl -k -b
journalctl -k -b -1
cat /proc/sys/kernel/tainted
```

Production crash handling may include:

- Persistent or remote journals.
- pstore for firmware-backed records.
- kdump and vmcore capture.
- Watchdogs for lockups.
- Machine-check and hardware-error telemetry.

Rebooting can be a mitigation, but it is not root-cause analysis and may destroy volatile evidence.

## 1.12 Interview drills

### Is a syscall a context switch?

It is a controlled privilege transition. A scheduler context switch to another task is separate and may or may not occur.

### Why is PID 1 special in a container?

It becomes the namespace init process, adopts orphans, must reap children, and has signal semantics that can surprise ordinary applications.

### Why can boot be slow when no service has a large startup time?

The delay may occur in firmware, initramfs discovery, device timeouts, mount dependencies, serialized ordering, network-online waits, or hidden activation paths. Analyze the end-to-end critical chain.

### Why can an accepted eBPF or kernel module still cause an outage?

Safety validation does not prove operational correctness. A logically valid program can consume excessive CPU, create map pressure, drop legitimate traffic, or amplify a control-plane error across every workload on a node.

## 1.13 Hands-on labs

1. Capture the boot critical path and identify one unnecessary serialized dependency.
2. Trace a disposable service with `strace -f -ttT` and classify time into filesystem, network, futex, and other waits.
3. Compare a blocking socket server with an `epoll` server under thousands of idle connections.
4. Observe `/proc/interrupts` and `/proc/softirqs` during a network load test.
5. Trigger a controlled service failure and reconstruct its timeline from monotonic journal timestamps.

## 1.14 Principal-level summary

> Linux performance is queueing across subsystem and privilege boundaries. I start with customer impact, trace the operation through userspace and the syscall boundary, locate where tasks block or queue, and validate the hypothesis with counters and profiles. I avoid random tuning because the same latency symptom can originate in scheduler delay, reclaim, locks, storage, networking, firmware, or a dependency outside the host.
